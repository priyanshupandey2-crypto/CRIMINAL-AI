Reflection Loop:
- Route function: route_review()
- Approval condition: "APPROVED" in review_result
- Retry limit: 2 (max retries)
- Behavior:
  ✓ If approved: Return final response (END)
  ✓ If rejected: Loop back to synthesis node
  ✓ If max retries: Return best attempt (END)

Example Flow:
Attempt 1: RAG -> Research -> Synthesis -> Reviewer
           Review: REJECTED (reason: incomplete)
Attempt 2: Synthesis (with feedback) -> Reviewer
           Review: APPROVED
Output: Final synthesized response

Total Workflow Latency (End-to-End):
- Best case (approved first try): 4.6-7.2 seconds
- Worst case (2 retries): 10-15 seconds
- Average: 6-8 seconds

Current Configuration:
```python

    model="gemini-2.5-flash",
    google_api_key=os.getenv("GOOGLE_API_KEY"),
    temperature=0.2,
)
```

Model Details:
- Provider: Google AI (Gemini)
- Model Name: gemini-2.5-flash
- Temperature: 0.2 (relatively deterministic)
- API Key: Loaded from environment variable
- Provider: LangChain Google GenAI integration

Usage:
- Synthesis Agent: Uses this LLM ✓
- Reviewer Agent: Uses SAME LLM ✓ (ISSUE - See Section 5.1)
- Orchestrator: Not using LLM directly
- RAG Agent: Vector search only, no LLM

CRITICAL ISSUE - SAME MODEL FOR REVIEW:
=========================================
Problem: Both synthesis and review use identical LLM configuration
- Model: gemini-2.5-flash (SAME)
- Temperature: 0.2 (SAME)
- No independent verification possible
- Reviewer bias towards approving generator output

Impact:
- Reduced quality of review process
- Hallucinations may not be caught
- Loss of critical evaluation layer
- Architectural flaw in reflection loop

Recommendation: Use different model for review
Proposed Solution:
```python
# Synthesis - creative/generative
synthesis_llm = ChatGoogleGenerativeAI(
    model="gemini-2.5-flash",
    temperature=0.2
)

# Review - strict/evaluative
review_llm = ChatGoogleGenerativeAI(
    model="gemini-2.0",  # Different, more capable model
    temperature=0.0      # Zero temperature for strict evaluation
)
```

7.1 FUNCTIONAL ISSUES

Issue 1: No Backend Authentication
Severity: CRITICAL
Location: backend/main.py
Impact: Any user can access /chat endpoint
Fix: Implement JWT authentication

Issue 2: Frontend-Only Authentication
Severity: CRITICAL
Location: frontend/src/context/AuthContext.jsx
Impact: Security bypassed with localStorage manipulation
Fix: Remove frontend auth, use backend tokens

Issue 3: Same LLM for Generation and Review
Severity: CRITICAL
Location: backend/config/llm.py
Impact: Reviewer cannot independently evaluate output
Fix: Use separate model for review

Issue 4: No Input Validation
Severity: HIGH
Location: backend/main.py (/chat endpoint)
Impact: Potential DoS, injection attacks
Fix: Add input length/pattern validation

Issue 5: Memory Loss on Server Restart
Severity: HIGH
Location: backend/workflows/graph.py
Impact: Chat history lost when server restarts
Fix: Use persistent memory store (database)

7.2 PERFORMANCE ISSUES

Issue 1: Slow Response Time
Severity: MEDIUM
Time: 6-8 seconds per query
Cause: Sequential API calls (Tavily, LLM, etc.)
Fix: Implement caching, parallel processing where possible

Issue 2: No Caching Strategy
Severity: MEDIUM
Impact: Repeated queries hit external APIs
Fix: Implement Redis caching for common queries

Issue 3: Infinite Timeout on API Calls
Severity: MEDIUM
Location: frontend/src/services/api.js
